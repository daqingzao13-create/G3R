## 0. 为什么要做这个新实验（动机）

### 0.1 现状问题

论文 §4.6「Joint Semantic and Spatial Analysis」（building–resident–origin 多尺度热点）
本质上仍然是一个**空间计算故事**：

- 卖点是「一张图里做多尺度聚合」比「跨库 ETL + 逐尺度渔网重算」快 9×；
- 但它证明的是 **G3R 的空间聚合效率**，不是 **语义与空间的融合推理能力**；
- 全文几乎都在讲「空间怎么算得又快又准」，**语义几乎不出场**。

而作者认为，本文真正最大的贡献落点应该是：

> **弥合「知识图谱语义关系」与「空间计算关系」之间的推理鸿沟。**

### 0.2 核心洞察：知识图谱里的「断点」

知识图谱很容易推出**语义链**，例如：

```
四川省 ←籍贯— 居民 —居住于→ 建筑B
医疗设施类型 ←类型— 医疗POI F
```

两段语义链各自完整，但**中间的空间关系缺失**：

```
建筑B    ?    医疗POI F
```

现实查询却大量需要这段空间关系：

- 哪个医疗设施离建筑最近？（KNN / 距离）
- 某设施是否位于建筑东北方？（方位）
- 建筑周围 800 m 内是否有医疗设施？（缓冲 / 范围）
- 建筑落在哪个地块上？该地块有哪些 POI / 建筑 / 住了多少人？（叠置 / 反向叠置）

知识图谱若想靠「边遍历」直接回答，就必须**预先物化**：

```
建筑B ──NEAR──→ 医疗POI F
建筑B ──NORTH_OF──→ 医疗POI F
建筑B ──800M_REACHABLE──→ 医疗POI F
```

但深圳 **56.2 万建筑 × 104.6 万 POI** ⇒ 潜在对象对约 **数千亿级**，
显式存边规模近 `O(n²)`，且对象一变就要重建。**不可能全量物化。**

> **结论：G3R 弥合的不是任意缺失语义关系，而是「知识图谱中因难以显式物化
> 而缺失的空间关系段」。**

### 0.3 G3R 的做法：构造「空间桥」（Spatial Bridge）

不直接建 `建筑B → 医疗POI F`，而是让两端各自挂到 GeoSOT 空间结构上：

```
建筑B
  → CC/VC/LCPC 编码 (覆盖网格)
  → GeoSOT 层级前缀 + 同层邻接路径
  → POI 所在网格
  → 医疗POI F
```

于是完整推理路径变成三段：

```
语义链A → 空间对象A → [G3R 空间桥] → 空间对象B → 语义链B
```

具体：

```
Semantic Path 1                Spatial Bridge (G3R)              Semantic Path 2
四川省 ←籍贯— 居民 —居住于→ 建筑  →  GC/VC/LCPC + 前缀/邻接/回退  →  医疗POI →类型→ 医疗设施概念
```

空间桥能实现：包含、方位、邻近、多尺度、KNN、连通空间搜索。

### 0.4 与「知识图谱路径发现」的区别（更精确的定位）

传统 KG 路径查询：在**已有边**里找 `A → ? → ? → B`。

G3R 不是从已有关系里找路径，而是：

> 已知语义端点（或端点类型）→ 先沿**已有语义边**定位空间对象
> → 再用 GeoSOT 结构**实现（realize）**原本未显式物化的空间关系。

两个过程：

1. **显式语义边遍历**（explicit semantic-edge traversal）；
2. **隐式空间关系实现**（implicit spatial-relation realization）。

用「实现 realize」而非「推断 infer」：距离/方位/包含**不是概率猜测**，
而是由编码 + 网格结构 + 几何计算**确定性得出**。

## 1. 要证明的价值（五层价值框架）

新实验要论证的核心命题（作者原话整理）：

> 你的价值不是「外置 PostGIS 不能完成」，而是
> **「空间关系是否进入统一图执行（unified in-graph execution）」。**

外置 PostGIS 能算，但它只是一个「被调用的几何计算器」（geometry calculator），
它无法把空间关系变成图里的一等公民。五层价值：

| 层级 | 价值主张 | 一句话 |
|------|---------|--------|
| L1 | **避免语义↔空间反复「出图—入图」** | 不用在图库和空间库之间反复搬运、转换、往返 |
| L2 | **空间关系是路径中的中间证据，不只是计算结果** | NEAR/NORTH_OF/CONTAINS 可作为可解释推理链的一环 |
| L3 | **调用精确几何前，用图结构提前剪枝** | 前缀/邻接/回退先砍掉绝大多数候选，再算几何 |
| L4 | **一次空间嵌入，支撑多种空间关系组合** | 同一份 CC/VC/LCPC 同时服务距离/方位/叠置/KNN/缓冲 |
| L5 | **对重复复合查询，摊薄预构建成本** | 语义链 + 空间桥的复合查询越多，单位成本越低 |

> 这五层价值，正是需要**一个全新实验**去系统性证明的东西。当前 §4.6 只
> 隐含触及 L1/L5，L2/L3/L4 几乎没有专门证据。

## 2. 实验骨架（待与作者逐步细化）

新实验的目标形态（初步，**待作者确认/修改**）：

一个**端到端复合语义-空间查询**，形如：

```
给定 [语义约束A]，通过 [空间关系] 关联到 [语义约束B]，返回 [聚合/列表/判定]
```

示例查询模板（医疗只是举例，可替换）：

- Q1：找出「四川籍居民所住建筑」周围 800 m 内的「社区医疗设施」，
  按建筑聚合统计设施数量 / 最近距离。
- Q2：某类居民关联的建筑，是否形成连续空间集群（连通搜索）。
- Q3：给定地块类型，反查地块内建筑 → 居民 → 户籍构成 + POI 服务供给。

对照基线（延续全文口径）：

- **G3R**：语义链遍历 + 空间桥（前缀/邻接/回退 + 局部几何）全部在**统一图执行**。
- **PostGIS + 图库分离**：语义在图库、几何在空间库，需跨系统「出图—入图」。
- （可选）**KG 预物化空间边**：证明 `O(n²)` 物化不可行（存储/构建时间爆炸）。

> **注意**：实验必须让「语义」真正出场——查询的**入口和出口都是语义约束**，
> 空间关系只是中间桥。这样才区别于前四个纯空间算子实验。

## 3. 可复用的现有算子（代码资产盘点）

新实验不重写几何核，而是**编排（orchestrate）现有算子**成复合查询。
以下为从代码库确认的可复用积木（相对 `GeoSot/` 目录）：

| 能力 | 主程序 | 关键入口 / 说明 |
|------|--------|----------------|
| 点-点/几何 距离 & 方位 | `geosot_spatial_reasoning.py` / `geosot_geometry_reasoning.py` | BFS EAST_OF/NORTH_OF 偏移累加 + Vincenty；9 种几何组合 |
| 正向叠置（地块→内部要素） | `geosot_overlay_query_v7.py` | 多分辨率填充 + 前缀匹配 + 边界 PIP（`_code_to_xy`, `_winding_number_batch`） |
| 反向叠置（点→所属地块） | `geosot_reverse_query.py` | LCPC 前缀回退 + 邻域扩展 + 绕数法 PIP |
| KNN 最近设施 | `geosot_knn_v3_1.py` | 严格 L2 覆盖判据 + 自适应邻域 + 距离精排（`POIPrefixCache`） |
| 多尺度语义-空间聚合 | `multiscale_kg_vs_postgis.py` | Neo4j 单图预加载 + 前缀截断 groupby + Gi*/HHI |
| 居民语义链应用 | `resident_hometown_knn_v3.py`, `resident_distance.py` | Resident→House→Building→GeoSOTCode 链路已打通 |

图 schema（论文 Table 2 / Appendix）：

- 空间码层：`GeoSOTCentroidCode` (CC) / `GeoSOTVertexCode` (VC) / `GeoSOTCommonPrefixCode` (LCPC)
- 层级骨架：`GeoSOTLevelDigit`k + `EAST_OF` / `NORTH_OF`
- 语义链层：`Resident` / `House` / `Building` / `DataSource` + `LIVE_IN` / `LOCATED_IN` / `FROM_SOURCE`

> 复合查询要做的，就是把「语义链层」的遍历和「空间码层 + 层级骨架」的桥接
> 串进**同一个执行流程**，并逐段计时 / 计候选 / 计精度。

数据规模（论文 Table 4）：建筑 561,553；POI 1,045,718；法定图则 40,570；
道路 12,274；居民记录 18,508,084；有效完整链居民 13,682,978；户籍来源 604 万。

### V0.5 — Resident 属性是否升节点（调研，决策待定，2026-07-14）

- **问题**：Resident(1850万) 有大量属性，哪些升成节点+关系、哪些留属性？
- **只读探查（`resident_attr_probe.py`）结果**：低基数高填充的分类字段有
  `sex`(3)、`nationid`(44)、`edulevelid`(11)、`domiciletype`(8)、`marryid`(6)、
  `politicsid`(6)、`techtitleid`(8,90.7%)、`tradeid`(9)、`bidefashion`(5)、

- **两点关键**：
  1. 这些字段**全是编码**（sex=1/2、nationid=01/08、edulevelid=6/5…），升节点前需先
     从 PostGIS `oracle_mig` 补 **编码→名称字典**，否则节点名不可读；
  2. **成本**：每升一维 = ~1850 万条边；不宜全升（属性+索引做过滤更划算）。
- **建议（决策原则）**：只升 2~4 个进 ② 复合查询且有公共服务叙事价值的维度，其余留属性。
  候选优先级：`domiciletype`(本地/外来人口, 公平性核心) > `nationid`(少数民族) >
  `edulevelid`(素质) > 派生**年龄段**(from birthday, 老龄化→医疗/养老)。
- **决定（2026-07-14，作者拍板）**：**Resident 各属性一律保留为属性字段，不升节点**。
  后续计算直接读属性过滤/分群即可；语义链一端已有 `CountyOrigin` 节点作代表，足够叙事。
  - 优点：省下近亿条边、过滤更快更简单、完全可逆（将来某场景需要再单独升某一维）。
  - 落地建议（做 ② 时再执行）：对常用过滤字段建索引，如
    `CREATE INDEX ... FOR (r:Resident) ON (r.domiciletype)` / `ON (r.nationid)`；
    编码→名称在查询/报表层做映射，不进图。

### V0.7.9 — 阶段B 精简反向叠置（forward_b）：bit 一致，实测受 PIP 内核封顶（2026-07-15）

用户选定「阶段B 改前缀桶批量空间连接（仍是 GeoSOT 算子，把逐栋级联 PIP 改成批量
向量化）—— 期望快 2–3x」。落地 + 剖析后得到**诚实结论：2–3x 不成立，因为阶段B 是
PIP 计算封顶，而 PIP 是算法必需的精确点-面几何测试，不可向量化消除。**

**做了什么**：新增 `_attr_one_lean()` 替代逐栋级联 `_cascade_prefix_query`：
- 只扫「索引里真实存在的前缀长度」`plens`（降序 24 档），跳过原级联 `tier_size=1`
  从 `len(cc)` 到 2 逐长度的空 tier 字符串切片 + dict 查询；
- 直接命中 `cp._index`/`get_bbox`/`get_polygon`，不建 row-dict / seen_mc / 候选 list；
- 语义严格保持：最细前缀 tier 优先（降序首个有 PIP 命中即停）、tier 内多命中取
  最小面积 —— 与级联 `tier_size=1` **逐位等价**。worker 精简路径不再连 Neo4j。

**一致性（`_tmp_verify_lean`，已清理）**：6000 栋随机样本，老级联 vs 精简
**不一致 0 / 6000**；全量 298k 跑一遍复对，地块集 Jaccard 0.984/0.996、六类 |Δ|=0m、
命中一致 99.7% —— 全部与 V0.7.8 完全相同。**零正确性风险。**

**为什么快不了 2–3x（`_tmp_profile_b`，已清理，6000 栋单栋耗时构成）**：
| 步骤 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| CC→xy 解码 | 98ms | 2% | lru_cache+位运算，已极小 |
| 前缀扫 dict.get | 77ms | 2% | 精简跳空 tier 后已极小 |
| bbox 预筛 | 1100ms | 24% | 874,079 次（~146 候选/栋），唯一可向量化项 |
| **PIP 绕数** | **3383ms** | **73%** | 8,693 次，~0.39ms/次，**算法必需的精确几何测试** |

即：我优化掉的空 tier 扫描（原以为是瓶颈）其实只占 4%；**PIP 占 73% 且不可约**
（异构多边形无法跨 polygon 向量化绕数）。哪怕把 24% 的 bbox 全向量化到 ~0，理论上限
也就 ~1.3x —— 与精简版实测 **1.28x**（老级联 4.08s→精简 3.19s，同进程同时刻）吻合。

**MP initargs pickle 成本核实（`_tmp_pickle_cost`，已清理）**：`pc` 23.5MB/dumps 217ms、
`cp_map` 1.8MB、`parcel_cls` 1.7MB —— 共享缓存 pickle 到 8 worker 仅数秒，非瓶颈；
之前担心的「MP 搬运占 70s」不成立。

**结论**：forward_b 已落地为「精简反向叠置」，bit 一致 + 单栋 1.28x（零风险，保留）。
但阶段B 已到**算法下限**：再大提速只能改 PIP 内核（近似/网格格包含替代精确绕数），
会破坏我们花力气证明的「精确 PIP 一致性」，故正式实验不做。与 V0.7.8 合并的总结论
一致：本机流水线已接近实践下限，算子硬优化全用上、8 物理核并行吃满、几何内核封顶。

② OS 文件缓存冷热（PG A / Neo4j A，已有 `--prewarm`）; ③ 跨库 FDW 联邦聚合本身
（PG A，架构固有，**压不动**，只能多次取中位 + 承认其慢）。

**落地 `--repeat N`**：预热一次后两侧各跑 N 次，收集每阶段耗时，末尾打印
**min / 中位 / max / 极差%** 汇总表（`_bench_summary` + `_med`）。正式表取「中位」列;
「极差%」大的阶段提示仍受负载干扰。冒烟 N=2 验证：各阶段极差 1–8%（2 次已收敛到个位%）。

**推荐完整稳态协议**（按有效性排序）：① `--repeat 3~5` 取中位（治 OS 调度噪声，最关键）;
② Windows 高性能电源计划 `powercfg /setactive SCHEME_MIN`（禁 CPU 降频，台式机计算
抖动头号原因）; ③ 关后台/杀毒实时扫描 + 项目目录加排除; ④ `--workers 8`（物理核, 不用
16 让超线程互抢）; ⑤ `--prewarm`（IO 对称）。

**正式取数口径（不变结论）**：以**分阶段中位 + 跨系统搬运次数**为准——阶段A（G3R
图内 ~56s vs PG 跨库 ~428s, 7–11x）与 transfer 0 vs 5 是机器无关的结构结论; 端到端给
中位并注明负载敏感。

### V0.7.13 — mismatch 档稳态正式结果（预热+repeat3）+ 优势归因修正（2026-07-15）

`--dtarget mismatch --workers 8 --prewarm --repeat 3` 全量。取每阶段中位为正式数字。

**稳态成本（中位, s）**：

### 7.2 核心问题：要素类型「全部塌缩进 GeoSOTCode」（作者担心属实）

`GeoSOTCode`（166 万）是**所有要素共用的单一标签**, 仅靠 `FROM_SOURCE→Source`

| Source | GeoSOTCode 数 | 有独立实体标签? |
|--------|-------------:|:--:|
| POI | 1,045,718 | ❌ 无 |
| Buildings | 561,553 | ✅ 有 `Building` |
| Statutory Plan（法定图则/地块） | 40,570 | ❌ 无 |
| Road | 12,274 | ❌ 无 |
| Community / Subdistrict / District（行政区） | 744 / 76 / 14 | ❌ 无 |

更糟的是：`GeoSOTCode` 节点上**混装了各要素的业务字段**（A3 该标签属性）——
建筑的 `BLDG_NO / BLDG_USAGE`、地块的 `PLOT_NAME / PLOT_NO / LU_CODE /
LU_FUNCTIO`、POI 的 `f1 / f2 / f3`、道路的 `dlmc / dm / kd / qd / zd`, 以及一堆
语义不明的 `field / field_1 / field_13…field_18`, 全挤在同一个节点标签上。

> 即：`GeoSOTCode` 同时扮演了两个角色——(1) 纯空间编码锚点; (2) POI/地块/道路
> 的**事实上的实体节点**（承载其业务属性）。这正是作者说的「本该分开的东西
> 全放到了一起」。只有 `Building` 被提升成了独立实体标签。

## 8. 应用案例 B：深圳城中村探查（G3R 图内多信号复合评分）

> 脚本：`urban_village_g3r.py`（Part1 评分 + Part2 聚类/核验，单脚本）。
> 探查脚本：`probe_urban_village.py`、`probe_uv_codes.py`、`probe_neo4j_uv_attrs.py`。

### 8.1 定位（重要：防"标准不科学"质疑）

城中村**无官方标签** → 本案例是**方法能力示范**，不是"权威城中村识别地图"。
论文口径必须：

- **框定为能力示范**：展示 G3R 能在一张图里融合「语义属性(外省籍/籍贯多样性) ⨝
  空间形态(握手楼间距/密度)」做复合推理；不声称识别准确。
- **准则引文献**：判别信号沿用城中村识别研究的通用准则（流动人口聚居 / 来源混杂 /
  中低多层自建 / 高密度紧凑肌理），非自定。
- **定性验证**：高分连片区叠到公认城中村（南山村/湾厦/白石洲/岗厦…）看命中。
- **敏感性分析**：权重扰动看连片区是否稳定（待补，见 8.6）。
- 全程标 **exploratory**。与 §4.6 / §8(错配) 的**客观定义**实验区别对待。

### 8.2 数据可行性（只读探查结论）

- **强信号（覆盖率已验证）**：`county_origin`（99%，2,926 种户籍地）、`layers`（86%，
  p50=3/p75=5/p95=8）、`buildtype`（100%，码1=住宅多层）、`buildingelevator`（90%）、
  `housearea`（100%）、`res_total`（已有）、握手楼间距（GeoSOT KNN 可算）。
- **剔除**：地块 `building_c`(容积率)/`green_perc`(绿地率) 绝大多数=0；`floor_area`
  文本多为 `--`；`salary` 仅 1%；`buildingelevator` 层数分离弱(3.7 vs 3.1)→降权。
- **关键发现（信号饱和）**：`domiciletype` 码表用 `county_origin` 推不干净（籍贯≠户籍
  二分），且"非深圳户籍"≈全民（深圳移民城市）→ **饱和、无区分力**。改用
  **「外省(非广东)占比」** 作外来信号，区分力显著提升。

### 8.3 信号集（等权，文献可支撑）

| 信号 | 定义 | 指向 |
|------|------|------|
| 外省占比 | `county_origin` 非'广东省' 比例 | ↑ |
| 籍贯多样性 | 每栋不同 `county_origin` 数 | ↑ |
| 中低多层 | `layers` 靠近 6.5（4–9 层握手楼典型） | ↑ |
| 居住密度 | `res_total / 建筑占地(clip 30–5000)` | ↑ |
| 握手楼间距 | **GeoSOT 最近邻建筑距离**（取反）← 空间桥·KNN | ↑ |

各信号 p5/p95 稳健归一化到 [0,1]，等权平均 = `uv_score`。

### 8.4 G3R 图内实现（全在 Neo4j，跨库 0）

- **Stage A** 图内聚合：`Building-[:HAS_GEOSOT]->GeoSOTCode` +
  `Building<-[:LOCATED_IN]-House<-[:LIVE_IN]-Resident` 单趟聚合，得每栋
  外省数/籍贯多样性/人口 + 建筑形态属性（`layers/buildtype/buildingarea/address`）。
  冒烟走"先取 Z-order 前 N 栋再仅对其聚合"两段式，真正随 `--limit` 缩小。
- **Stage B** 空间桥·KNN：以**全体建筑 CC 为目标集**，逐栋 `knn_search(k=2)` 取第一个
  非自身邻居距离 = **握手楼楼间距**（复用 `geosot_knn_v3_1`，召回强化档）。
- **Stage C** 归一化 + 等权评分 → `csv/uv_building_score.csv`。

### 8.5 聚类 + 核验（Part2，无 sklearn）

- **Stage D** 米制网格连通分量聚类：高分建筑（默认 top 15%）取质心（PostGIS
  building_new 投影 4547，仅几何、非评分环节），150m 网格 8-邻接 union-find →
  候选连片区（≥min_bldg 栋）。
- **Stage E** 命名 + 核验：按 `Building.address` 众数村名标签；对公认城中村关键词
  + "含村/旧村/围/坊"名字自证做定性核验 → `csv/uv_clusters.csv`。

### 8.6 冒烟结果（`--limit 6000`，落在 南山/蛇口 区块）

端到端 6–11s（A 4.8s / B 2.1s / D+E <1s，跨库0）。Top 候选连片区：

| # | 名称 | 栋 | 人口 | 均分 | 证据 |
|---|------|---:|-----:|-----:|------|
| 1 | 南山村西 | 479 | 35,245 | 0.717 | 公认✓ |
| 2 | 后海 | 110 | 15,379 | 0.730 | 公认✓ |
| 3 | 蛇口湾厦旧村 | 230 | 15,175 | 0.721 | 公认✓ |

| 6 | 蛇口商乐村 | 23 | 3,625 | 0.717 | 公认✓ |

### 8.8 G3R vs PostGIS 对比实验（`run_urban_village_experiment.py`）

镜像 `run_mismatch_experiment.py` 的结构与严谨度：**两侧走同一套 `stage_c`
归一化+等权评分**（公平），只在"怎么拿到信号"上不同：

| 阶段 | G3R 图内 | PostGIS 外置 |
|------|----------|--------------|
| A 聚合(外省/籍贯/人口+形态) | Neo4j 语义链单趟聚合(跨库0) | oracle_mig 跨库 resident→house→building 聚合(搬运1) |
| B 握手楼最近邻建筑距离 | 空间桥·KNN(GeoSOT 网格) | 投影米制 GIST `<->` 自连接 |
| C 归一化+等权评分 | 同一 `stage_c` | 同一 `stage_c` |

**冒烟（`--limit 6000`，两侧同批 main_code 对齐）结果**：

- **一致性**：高分集 Jaccard **0.992**；语义信号(居民/外省/籍贯数)逐栋 **100% 完全一致**；
  握手楼距离 中位|Δ| **0.04m** / P99 0.45m / 相关 **0.9955**；复合评分 中位|Δ| **0.0008** /
  相关 **0.9997**。→ 两套独立实现互证：算的是同一件事。
- **成本**：Stage A **G3R 3.3s vs PG 112.3s（~34×）**；Stage B G3R 2.3s vs PG 1.3s(PG 几何略快);
  端到端 5.7s vs 114.0s；跨系统搬运 **0 vs 3**。
- **优势归因（与 §4.6/错配实验一致）**：核心优势在 **Stage A 图内语义聚合**——PG 跨库联邦
  无法把建筑过滤下推，仍需扫 1,850 万居民；G3R 图内遍历只碰相关居民。几何算子(握手 KNN)
  PG 仍略快，不是 G3R 卖点。**论文应强调"消除跨系统搬运 + 图内语义-人口聚合"**。

**全量命令**（机器空闲时自己跑）：`python run_urban_village_experiment.py`
（PG Stage A 全量跨库聚合是主要耗时，约数百秒且随机器负载波动；G3R Stage A 图内 ≈50–90s）。

#### 8.8.1 全量实测 + 握手楼 KNN 提速 (V0.8.1)

**首次全量 (握手 KNN 旧参 min_margin_m=300/max_widen=11)**：一致性完美 ——
高分集 Jaccard **0.989**、语义信号逐栋 **100% 一致**、握手 |Δ| 中位 **0.03m** /P99 0.34m
/相关 0.9926、复合评分 |Δ| 中位 0.0007/相关 0.9998。**成本**：A 聚合 G3R 51.0s vs
PG 282.1s(**5.5×**)；**B 握手 G3R 414.0s vs PG 27.4s(PG 15×)** ← 全市 29.8 万栋
all-buildings self-KNN, G3R 逐栋查询 vs PG GIST 集合级索引自连接; 端到端 G3R 466s
vs PG 312s(**PG 反超**)；跨系统搬运 0 vs 3。

**问题定位**：B 慢是因 KNN 用了"召回强化档"(300m 保证半径), 而握手邻居中位仅
**13.6m** → 每栋在 300m 大范围里搜一个 13m 外的邻居, 城区 300m 含大量建筑 → 候选爆炸。

**提速 (V0.8.1)**：`_HS_KW` min_margin_m 300→**50**、max_widen 11→**8**; 并修隐患:
KNN 真找不到邻居时兜底由 `0.0`(误判极紧凑高分) 改为 `_HS_MISS=1000.0`(低握手分)。
- **实测提速**：40k 块 B 由 ~0.7k/s → **~3.1k/s**(12.9s), 全量 B 预计 **~96s**(原 414s, ~4×)。
- **精度无损**(冒烟 `--limit 8000` 对 PG)：握手 |Δ| 中位 **0.03m**/P99 0.54m/相关 **0.9956**;
  Jaccard **0.992**; 语义 100%; 评分 |Δ| 0.0001。
- **新全量实测 (V0.8.1 确认)**：

  | 阶段 | G3R(s) | PG(s) | 备注 |
  |------|-------:|------:|------|
  | A 语义+形态+人口聚合 | 54.9 | 207.6 | G3R **3.8×** (图内 vs 跨库) |
  | B 握手楼 KNN | 120.5 (2.47k/s) | 27.9 | PG 4.3× (原 15×, 已大幅收窄) |
  | C 评分 | 1.3 | 1.4 | — |
  | **端到端** | **176.8** | 239.7 | **G3R 1.36× 反超** |
  | 跨系统搬运 | **0** | 3 | — |

  一致性仍完美: Jaccard **0.989** / 语义 **100%** / 握手 |Δ| 中位 **0.03m** P99 0.34m
  相关 0.9923 / 评分 |Δ| 0.0007 相关 0.9998。
- **结论 (与错配实验一致, 可写论文)**：城中村探查中 G3R **端到端更快(1.36×) + 零跨系统
  搬运 + 结果与 PostGIS 逐栋等价**。优势主要来自 **Stage A 图内语义-人口聚合(3.8×)**;
  纯几何算子(握手 self-KNN)PostGIS GIST 仍略快(4.3×), 但经调参已非瓶颈。**论文叙事应
  强调"图内语义-空间融合 + 消除跨系统搬运", 而非声称击败专用空间索引。**

#### 8.9.1 汇聚粒度：按法定图则地块 (V0.8.3, 默认)

原 `--by grid` 是"高分建筑质心 → 150m 网格 → 8邻接连通分量 → 成员凸包"，范围是凸包、
易把邻近村连成巨片。改为 **`--by parcel`（默认）按法定图则地块汇聚**：

- **归属**：复用错配实验 `csv/g3r_parcel_attribution.csv`（GeoSOT 点-面反向叠置，
  building_cc→parcel_main_code；全市 **79.8%** 建筑落到真实地块，涉 18,709 个有居民地块）。
- **汇聚**：建筑 `uv_score` 按 `parcel_main_code` **人口加权**聚到地块
  （`score_pw = Σ(score·res)/Σres`），并记 `hi_frac`=地块内高分楼(≥建筑 top15% 阈值)占比。
- **筛选**：`score_pw ≥ 建筑阈值(0.698)` 且 `≥5 栋` 且 `≥300 人`。
- **画范围**：直接取 `public.statutory_plan`（40,570 地块, SRID 4490）的**真实地块边界**
  （ST_Transform→4326/3857, 支持 MultiPolygon 多环），非凸包。

**结果**（全量, top=0.15）：**1,165 个候选地块**；命中公认城中村关键词 **61/1165**、
名字自证村落(含公认) **455/1165**。Top 人口候选直接是公认城中村地块——
岗厦村东三坊(公认*)/上沙龙秋村(公认*)/上白石三区(公认*)/上沙东村(公认*)/沙咀村二区/
水斗富豪新村…卫星特写中红色地块边界**精准套住"握手楼"高密度肌理**、四周为规整高层
（如 #1 岗厦村东三坊嵌于福田 CBD），face validity 极强，且比网格凸包更规范、更贴单个村。

**产物增量**：`csv/uv_parcels.csv`（候选地块清单: 地块码/村名/用地类/栋数/人口/加权分/
高分占比/是否公认）、`paper_figures/uv_parcel_buildings.csv`（地块成员建筑）。

**可调**：`--parcel-th`(地块加权分阈值) / `--min-bldg` / `--min-res` / `--by grid`(切回网格法)。

**`--merge`（相邻地块合并成整村, V0.8.4）**：城中村常跨多个相邻地块(如岗厦分东/西+多坊)。
加 `--merge` 后，用 shapely STRtree + 并查集把**间距 ≤ `--merge-gap`(默认20m)** 的候选地块
分组，每组 `unary_union` 出整村轮廓(保留真实地块边、不做缓冲变形)；属性按人口无损再汇总
(`score_pw = Σssum/Σwsum`)。结果：**1,165 地块 → 739 连片村**；命中公认 **33/739**、
村名自证 283/739。如 #4 岗厦村东三坊由 4 地块溶成一片(367栋/27,106人)，卫星特写中整村
轮廓四至贴合周边道路，比单地块更完整。产物：`csv/uv_parcels_merged.csv`。
```
python make_uv_figures.py --merge                 # 整村轮廓(gap 20m)
python make_uv_figures.py --merge --merge-gap 30  # 桥接更宽道路
```

#### 8.9.3 出图样式细化 + 阈值放宽 (V0.8.6)

按论文进一步要求调整:
- **只出范围图**：`--range-only`（不出纯影像图, 省一半文件）。
- **细边界线**：`--line-width`（默认 **0.8**, 原 2.0 太粗）。
- **默认改黄**：`--color` 默认 `#FFFF00`；填充 `--fill-alpha`（默认 **0.12** 淡填充, 0=只描边）。

**判别过严 → 放宽阈值**：原 `--top 0.15`(建筑高分阈值 0.698)偏严, 图上一些真城中村漏判
(注意: 密集**高层**区因"中低多层(4–9层)"信号本就低分, 属正确排除, 非漏判)。阈值敏感性:

## 9. 规范化语义层级解析（V0.9，两侧对称 + 细粒度耗时）

**动机**：让 PostGIS 与 G3R 走**同一套**"叶子 + 层级树/字典"语义解析，而非各自用冗余
捷径（PG 直读 `f1/f2`、图直连大类边、籍贯截字符串前缀）。这样 (a) 两侧语义模型一致、
更公平；(b) 把"层级解析代价"显式暴露，配合逐小步耗时看清 G3R 的真实优势所在。

三套结构由 `build_semantic_hierarchy.py` **幂等**构建（只增不改）：

| 维度 | 图（Neo4j） | PG | 一致性验证 |
|------|-------------|----|-----------|
| POI 种类 | 已有 `(:POIType3)-[:SUBCLASS_OF]->(:POIType2)->(:POIType)`；改为**只走叶子** `HAS_POI_TYPE_3` + 上溯 | 已有 `gaode_poi_category`；`poi_new` **只用叶子码 `poi`** join `poi编码` 展开大/中类（补索引 `ix_poi_new_poi`/`ix_gaode_code`） | 六类计数 vs 旧 `f1/f2` 逐类 **Δ=0** |
| 地块类型 | 新建 `(:LUClass)/(:LUSubtype)` + `(LUFunctionGroup)-[:IN_LU_CLASS]->` | 新建 `lu_function_dict(lu_name→land_class/subtype)` 465 行 | 两侧类别均由 `landuse_norm.classify` 派生 → 逐名一致 |
| 籍贯 | 新建 `(:Province)/(:AdminCity)` + `(CountyOrigin)-[:IN_PROVINCE]/[:IN_CITY]->` 各 2926 | 新建 `oracle_src.county_origin_dict(name→province/city)` 2926 行 | 省/市由 `admin_norm.parse_admin` 派生，与 `STARTS WITH` 前缀在 **18.5M 居民 Δ=0**（外省/非深两口径） |

**流程改动（对称）**：
- POI（错配 阶段D）：G3R `service_categories` 走 `HAS_POI_TYPE_3-[:SUBCLASS_OF*]->` 到目标大/
  中类；PG 先在 `gaode_poi_category` 上按大/中类解析出叶子码集合，再 `poi_new.poi = ANY(codes)` 过滤。
- 地块（错配 阶段C）：G3R 走 `IN_LU_CLASS` 图层级推理；PG 查 `lu_function_dict`（非应用层关键词）。
  组合(混合逻辑)抽出为共享 `_combine_classes`，两侧一致。
- 籍贯（城中村 阶段A）：G3R 走 `(r)-[:HAS_COUNTY_ORIGIN]->(:CountyOrigin)-[:IN_PROVINCE]/[:IN_CITY]->`；
  PG `LEFT JOIN county_origin_dict` 解析省/市。

**细粒度分步耗时 CSV**（新增，每个小步一行）：
- 错配：`csv/mismatch_step_timings.csv`（engine/stage/substep/sec/rows/note，38 子步）。
- 城中村：`csv/uv_step_timings.csv`（8 子步）。
- 控制台 `[4b]` 段按引擎/阶段打印，语义解析子步单列。

**冒烟核验（结果不变）**：
- 错配 `--limit 4000`：六类 POI 计数逐类 Δ=0，基准 Jaccard **1.000**、错配 0.943（沿旧 PIP vs
  反向叠置边界差，非本次回归），同 POI 命中率 99.6–99.9%、MAE ~0.4m。
- 城中村 `--limit 5000`：逐建筑 **外省人数/籍贯种数 100.0% 一致**，uv_score 相关 0.9996。

**关键结论（诚实归因）**：语义层级解析本身**两侧都很便宜**（POI 类树上溯 0.2–0.9s/类、PG 叶子码
join 0.001–0.17s；用地/籍贯 join 更是毫秒级）——即"假设只有叶子码/籍贯全串再 join 展开"**并不会
大量拖慢 PostGIS**（字典表小 + 有索引）。G3R 的真实、可辩护优势在**零跨系统搬运 + 图内统一遍历**：

细粒度 CSV 正好把这一点逐步坐实。

### 10.2 运行环境调优（关键：内存过配 + 机械盘）

复跑时磁盘长期 100%。诊断（本机 63.7G 物理内存）：

- **Neo4j 内存过配**：原 `heap 20G + pagecache 38G ≈ 58G`，再叠 PG(7 进程)+ 8 个 Python worker + OS，
  提交内存冲到 **149G**（物理 2.3×）→ Windows 用 pagefile 换页 → 磁盘打满、首跑阶段A 千秒。
  改为 **`heap 10G / pagecache 20G / tx 6G`**（`neo4j.conf`，重启生效）；页缓存实测用满 19.56/20G，
  刚好托住 G3R 热集 → **G3R 首跑尖峰消除、阶段A 稳定 ~37–56s**。
- **真正的硬件瓶颈是机械盘**：数据(Neo4j 库 38G、PG 库 35G)全在 **D: = TOSHIBA 2TB HDD**；
  C: 为 NVMe SSD(空闲 77.5G)。HDD 随机读极慢(冷读 34G≈1027s)，两库在 64G 内存里抢缓存、
  谁跑就把对方缓存踢到盘上 → PG（单实例 `shared_buffers` 仅 128MB、`work_mem` 4MB）每轮冷读机械盘。
- **建议(待办)**：把 PostgreSQL 数据目录 `D:/app/postgresql/data`(35G) 搬到 SSD(C:)；
  `work_mem`→256MB、`effective_cache_size`→16G；或**分开基准**(`--only g3r` / `--skip-g3r`)避免两库互踢缓存，

## 11. 指标体系复杂度 & 结构演化代价实验（V1.1）

**动机（作者猜想）**：城中村这类判定天生是**复杂、异构、多跳、且持续演化**的复合指标
体系。作者主张:①**执行代价**——指标体系越复杂、跨越越多结构不同的异构族/存储, PostGIS

### 11.1 全量首跑修正 + 交织族补充（V1.1.1，2026-07-18）

**全量首跑(4族13指标, `--workers 8 --prewarm --repeat 3`)结果与教训**：
- 一致性完美(语义100%、握手0.028m、地块98.0%、POI 99.7%)。
- **结构证据(规模无关, 论点核心)**：跨系统搬运 **0 vs 7**、独立存储 **1 vs 4**、临时表 0 vs 9、
  索引 0 vs 8；PG 每族 SQL 语句 1/37/35/72。
- **时间(每族中位)**：G3R 合计 **~362s** vs PG **~399s** = 仅 **1.1×**；分族 semantic G3R 57 vs
  PG 247(**4.3×**), 但 handshake/overlay/poi 三个几何族 **PG(GIST) 反而更快** → 稀释总优势。
  PG semantic 极差 **240%**(211→805s, 机械盘缓存争用离群), G3R 全族极差≤34%。
- **修 Bug**：`report()`/CSV 原用**最后一轮**(恰是 PG 805s 离群轮)→ 改为 `--repeat` 时用
  **每族中位**写 CSV/出图/汇总, 避免正式数字被离群值污染。

**关键认知(诚实, 必须写清)**：对**全体实体的批量指标**, 会"一次 bulk 拉全量语义再本地合并"的
PostGIS 很难被时间碾压——**独立几何指标越堆, 越是给 PG 擅长的 GIST 加战场, 反而稀释 G3R**。
"指标越多→G3R 越快"这个直觉, 在**独立指标堆叠**下不成立。G3R 时间优势能随复杂度**放大**的前提是
指标为**交织式**: 计算需在**分处两库的空间关系与语义链之间反复横跳**, 使 PG 每个指标多一次跨库
重聚合/往返, 而 G3R 只多一条图内路径。

**交织族(第5族, 2 指标, 自然城市语义"老乡聚居")**：
- 邻里同乡聚集度 = 每栋最近 8 邻里中主导籍贯省与本楼相同的比例；邻里外省浓度差 = 本楼外省占比
  与邻里均值之差。二者需 **每栋主导籍贯省**(PG 要做 `building×province` 跨库**重聚合**, 比标量族更重)
  + **空间 k 邻居**(GIST/图内 KNN) → **oracle_mig⨝postgis 两库交织**。
- G3R: `建筑—NEAR→建筑←House←Resident→CountyOrigin→Province` 同图一次遍历(搬运0)；
  PG: 先几何库 GIST 取邻居对, 再跨库 building×province 重聚合取主导省(搬运3)。
- **机制**: 每加一个交织/语义深指标 = PG 多一次跨库重聚合(全量下对 1850 万居民再扫一遍),
  G3R 只多一次图内遍历 → **这才是复杂度放大 G3R 优势的真实来源**(与 semantic 族同理)。

### 11.2 三臂对比（有图 / 联邦 / 物化）+ 结构演化代价（V1.2，2026-07-18）

**动机（作者质疑）**：全量 1.3× 的时间优势"不够明显"，尤其交织族。根因是当前对比把两件事
混在一起：①"图带来的好处"与②"PG 被迫跨系统吞吐的坏处"。反方最强反驳是"**把 PG 物化就没有
吞吐了**"。为拆开二者、并正面回应该反驳，引入**三种存储/执行策略**与**结构演化代价**实测。

**三臂（同一套 15 指标）**：
- **Arm A｜G3R 图内即时**：指标体系 = 图 schema；查询 = 图内遍历。改结构 = 加一条遍历/改一个参数。
- **Arm B｜PG 联邦即时**（= 原基线）：指标"活在"分离存储（居民 oracle_mig / 几何 postgis）；
  每族一次跨系统往返搬运。
- **Arm C｜PG 物化合并表**（新增，无图）：把整套指标拍平进一张 `ic_indicator_mat`（cc + 16 列）；
  稳态查询 = 全表 SELECT（近 0）。**代价**：(a) 一次性 build（须先按 B 算全套再落库+建索引）；
  (b) 每次结构演化都要**重付物化**（重建中间体 + 级联回填依赖列）。

**关键论证（诚实、抗审稿）**：物化用**一次性 build 换取查询速度**，但把"结构"烤进了表与中间体
→ 交织指标一旦定义变动即触发**级联重物化**；而 G3R 把结构编码进关系与算子，**改结构≈改查询**。
因此在"**复杂且持续演化**"的交织指标体系上，图的**总拥有成本（建+查+改）最低**；纯几何批量算力
不是图的主场，也不该作为卖点。

**结构演化实测（`--evolve`，两个代表性改动，三臂各测边际代价，全部实测）**：
- **EV1 ADD**：新增"邻里居住密度均值"（派生自已有邻居 + 居住密度）。
  - A：复用图内已遍历的邻居，仅一次数值装配（≈0）。
  - B/C：邻居中间体（临时表）已释放 → 必须**重建邻居**；C 另需 `ALTER TABLE` 加列 + 回填。
- **EV2 MODIFY**：把邻居定义 `k=8→12`（改一个**共享定义**）。
  - A：图内改一个参数，重遍历交织族即可，零 DDL。
  - B：整条交织族按新 k 重跑（含跨库主导省再聚合）。
  - C：**级联**——重建邻居 + 跨库重聚合 + 回填所有邻居派生列（coorigin/outprov_gap/…）→ 最贵。

**产出（新增）**：`csv/indicator_evolution_cost.csv`（EV1/EV2 三臂边际耗时 + DDL/临表 + 级联标记）、

### 11.3 指标体系元图（Indicator Meta-Graph，V1.3，2026-07-18）

**动机**：前述"图内优势"来自**基础实体关系图 + 算子**, 指标是按需遍历算出的, 并未把"指标体系"
本身存成图。为让"**指标体系本身是一张图**"字面成立(并正面支撑"改结构=编辑图"), 新建一层元图。

**建模**(命名空间隔离, 全部 `Meta*` 标签 + `sys='uv_ind_v1'`, **绝不碰基础实体图**, `--drop` 可清除)：
- 节点 `:MetaIndicator`(15指标 + 2中间量 neighbors/dominant_province + 演化新增 nbr_density)、
  `:MetaOperator`(SemanticAggregate/HierarchyTraversal/KNN/ReverseOverlay)、`:MetaEntity`(8类基础实体)、
  `:MetaParam`(如 neighbors.k=8)。
- 边 `DEPENDS_ON`(指标↔上游指标/中间量)、`USES_OPERATOR`、`READS_ENTITY`、`HAS_PARAM`。

**关键用途(结构证据, 与演化实验的"时间证据"互补)**：
- 指标体系规模 = 图规模; "改结构"= 编辑图(加指标=加1节点+若干边; 改共享定义=改1个 MetaParam)。
- **变更波及集 = 一条图可达性查询**：`MATCH (i)-[:DEPENDS_ON*]->(t{name:target})` 即 target 变动时
  须重算的所有下游指标。例：改 `neighbors.k` → 波及 {coorigin, outprov_gap, nbr_density}——**这正是
  Arm C(物化)必须级联重物化的那批列**(对照演化实验 EV2), 而 Arm A(G3R)只是"重走这几条遍历"、0 schema。

**产出**：`csv/indicator_metagraph_{nodes,edges,impact}.csv`、`paper_figures/indicator_metagraph.mmd`
(Mermaid 依赖图, 论文配图)、可选 `indicator_metagraph.png`。

### 11.4 图驱动指标引擎（Graph-Driven Engine，V1.4，2026-07-18）

**动机（作者关键要求）**：只有让 G3R **真按图里存的指标体系执行**, "在图上做推理"才名副其实;
若指标体系烤死在代码里(物化), 则证明不了论点。据此把元图从"描述"升级为"**可执行计划**",
并新建图驱动引擎按计划执行。

**合理边界（论文表述）**：算子(KNN/语义聚合/反向叠置/层级遍历)是**引擎固定原语**(本就该在代码里,
如同 DB 执行算子); **指标体系(有哪些指标、如何组合、依赖谁、参数几何)才是"数据", 存在图里**。
G3R = 引擎读图里的执行计划(拓扑序 + 参数) → 用原语在**实体图上遍历执行**。改指标体系 = 改图。

**实现**：
- `build_indicator_metagraph.py`：`IND` 升级为可执行声明(dict), 每指标加 `compute`(stage_a/
  knn_self/knn_neighbors/dominant_province/reverse_overlay/poi_knn/compose) + `field`/`cat`/
  `compose`/`src` 属性, 写进图节点; `neighbors.k` 为 `MetaParam`。
- `indicator_engine_g3r.py`(新建)：`load_plan()` 从图读指标+依赖+参数并**拓扑排序**;
  `Engine` 惰性调度各原语(复用已验证的 `uv_stage_a`/`uv_stage_b`/`g3r_overlay`/`g3r_poi`/
  `_neighbors_g3r`), compose 泛型(same_frac/nbr_mean/self_minus_nbrmean)按图执行; 产出每栋
  15 指标向量。**一致性校验**：图驱动泛型 compose vs 硬编码 `_compose` 中位|Δ| 应 ≈0。
- **演化=纯图操作, 零代码**：`--set-param neighbors k 12`(改共享定义) / `--add-nbr-indicator
  <name> <src>`(加邻里均值指标=加1节点+2依赖边), 改完重跑引擎即生效; 对照物化需改代码/ALTER+级联重物化。

**产出**：无新增 CSV(执行结果与 §11.2 一致, 引擎复用同一批算子); 关键价值是**架构证据**——
指标体系是可被引擎读取执行的图数据, "G3R 在图上推理"字面成立。

### 11.5 判别式迭代级联：联邦"逐跳跨库"成本的正面证据（V1.5，2026-07-20）

**动机（作者关键质疑）**：§11.2/§11.4 四臂里 **Arm Y（PG↔Neo4j 联邦）反而最快**，与作者
直觉"两库反复读取应很慢"相悖。溯源结论：那套 15 指标是**批量族**——每族**整批**从 Neo4j 导
语义再算，批量吞吐把跨系统开销摊没了（一次搬运服务几十万栋）。也就是说，只要指标能"整批预取"，
联邦并不慢；**跨库成本只有在无法整批时才暴露**。

**作者洞察（本节要验证的）**：真实的复杂指标体系含**判别指标**——先算一个指标，**再回图里看
这个结果决定下一步算什么**，是**数据依赖、变深度、分支**的控制流。此时无法预先批处理：不同种子
在不同深度停下、走深的还要沿路继续取数，联邦必须**逐跳**在 空间(PG) 与 语义(Neo4j) 间来回，
批处理失效，跨库往返真实发生。

**粒度演进（V1.5 逐建筑 原型 → V1.6 逐地块，作者要求）**：V1.5 初版以**建筑**为种子做"连片
生长"级联；作者指出真实城市诊断以**地块**为基本单元，且第一步"地块→其上建筑"正是**正向叠置**
（多边形→被包含要素，`geosot_overlay_query_v7.py` 一类；反向叠置是点→地块）。V1.6 遂改为
**逐地块**：更贴合应用语义，且把 G3R 招牌算子"正向叠置归属"放进判别链首步。以下为 V1.6 现行设计。

**判别级联设计（逐地块；种子=代表楼，一条诊断路径，空间↔语义逐步交替、变深度）**：
- 步骤1 **正向叠置（空间）**：地块 → 落其上的建筑集合；建筑数 `< Nmin` → "零星/空地"停；
- 步骤2 **语义链（语义）**：建筑→居民 聚合地块人口/外省占比；外省占比 `< T1` → "本地社区"停；
- 步骤3 **形态（语义/形态）**：地块建筑平均层数不在 `[Llo,Lhi]` 握手楼区间 → "非城中村肌理"停；
- 步骤4 **语义**：地块居民主导籍贯集中度 `< Tconc` → "混杂来源"停；
- 全过 → "强特征城中村地块"。
关键：**每算一个指标看结果再决定是否算下一个**（判别式），不同地块在不同深度停下 → **无法整批**。

**两后端（同一套级联逻辑，只换取数实现）**：
- **Arm A｜G3R 图内**：一次装载（正向叠置归属"地块↔建筑" + 语义/层数/主导省字典），之后逐步
  **全内存**，跨系统往返 **0**——判别路径在同一张图里走。
- **Arm Y｜联邦 on-demand**：预载仅建筑质心 GIST 点表；每步**现查**——"地块→建筑"打 PostGIS(GIST)，
  人口/层数/籍贯打 Neo4j，**每算一个指标一次跨库**。判别数据依赖、**无法整批**，往返真实发生。

**阈值校准（地块级，数据驱动）**：建筑数/地块 p50=3/p75=7/p90=27 → **Nmin=5** 筛零星地块；
外省占比 p50=0.67 → **T1=0.7**（放行 ~40%）；平均层数 p50=6.0/p90=16 → 握手楼区间 **[3,10]**
（排高层）；**Tconc=0.4**。种子=有归属地块的建筑，宇宙内随机采样。

**PG 查询优化（V1.6 关键、诚实）**：初版 Arm Y 每地块 **1.26s**——`ST_Contains(poly, ST_Centroid(
b.geometry))` 对被索引列 `b.geometry` 套函数，**GIST 失效 → 全表扫 29.8 万栋算质心+PIP**。改为
**预载时把建筑质心物化成带 GIST 的点表 `dc_bctr`**（与 G3R 建自己索引对等），每地块降到 **~22ms**
（≈2.6 次往返×8.5ms）。Y 级联 **1406s → 26.5s**，一致率 **87.5% → 98.6%**（两臂同 universe 质心集，
成员判定对齐）。⚠ **优化前的 9,400× 是慢查询假象，优化后 447× 才是真·跨库往返成本** —— 写论文
只用优化后口径。

|------|------:|------:|------:|------:|
| Arm A｜G3R 图内一趟 | 31.9 | 0.06 | **0.05** | **0** |

  即 1,505 个，全市数万）远多于此 → **批量扫全城 G3R 总账也赢**。

- 全市 **18,709 个有居民地块**逐块诊断（每块一次, 无重复; 非居住地块无居民故不在范围内）；识别

**★ 四臂单查询对比（V1.7，作者要求"补 X/C 两臂"，把逐地块判别级联做成真·四臂）**：
此前逐地块级联只有 A/Y 两臂；为与 §11.2 批量四臂口径对齐，补 **Arm X（PG 原生联邦）** 与
**Arm C（物化）**，四臂**跑同一套判别级联、同一批种子**，只换执行后端：

- **Arm A｜G3R 图内**：正向叠置归属 + 语义/层数/主导省字典一次装载，之后逐步全内存，往返 **0**。
- **Arm C｜物化**：全市地块诊断标签**一次算好落带键关系表**（`dc_mat`），稳态查询=**单行 SELECT**；
  极快但**静态**——阈值/规则一改整表须重物化（演化代价见 §11.2）。
- **Arm Y｜PG⨝Neo4j**：空间打 PostGIS(GIST 质心点表)、语义每步现查 **Neo4j**，逐跳跨库。
- **Arm X｜PG 原生联邦**：空间打 PostGIS、语义每步现查**关系库 `oracle_mig`**（`main_code→BLDG_NO`
  对齐后逐跳 `resident⨝house⨝county_origin_dict` 聚合）。即"两库都是关系库"的纯关系联邦。

⚠ **X 的暖/冷口径（诚实交代）**：`oracle_mig` 是**全市规模关系库**（居民 1,850 万 / 房屋 1,240 万，
本机置于机械盘）。冷缓存下每个**新地块**要在千万行表里做随机磁盘寻址，实测单个未命中地块 `pop`
一跳可达 **~18s**（纯磁盘 I/O 主导，非范式代价）；一旦相关页进缓存则降到 ~50ms/跳。按**暖缓存协议**
（与 A 内存、Y 图页缓存对齐）以**第二过（暖）**为口径，同时另列冷首过。程序对 X 做"冷首过→暖再过"
两遍、以暖为准。

| Arm A｜G3R 图内一趟 | 108.6 | 0.04 | **0.085** | **0** | — |

- **判别深度分布逐档吻合** A `{46,244,21,57,132}` / Y `{49,240,21,59,131}` / X `{49,240,20,63,128}`；
  **一致率** Y **98.6%**、X **96.4%**（X 略低: 语义取自关系库 `oracle_mig` 而非 Neo4j，除边界 PIP

**结论（与 §11.2 形成闭环，正面回应"Y 为何不慢"）**：
- **批量族**（§11.2 那 15 个可整批预取的指标）→ 联邦可一次搬运摊薄开销，Y 最快，图不占速度优势；
- **判别族（逐地块 on-demand）**→ 批处理失效，联邦被迫每算一个指标一次跨库，**每查询 447× 变慢、
  往返 0 vs 3,125**，G3R 图内全内存零往返。二者合起来说明：**指标体系一旦含判别/迭代结构（数据
  依赖、变深度、以地块为单元的正向叠置+语义交替），"图内统一遍历"相对"跨系统联邦"的优势才真正
  显现**，且这正是复杂城市诊断（城中村地块识别）的天然形态。
- 论文口径：不把"单点批量速度"当唯一卖点；强调 **G3R 在"数据依赖的逐地块判别级联"上避免了逐步
  跨系统往返**——跑**全部 18,709 个居住地块**时每查询 **324×**、跨库往返 **0 vs 34,450**、且**一次性
  总账亦领先（125s vs 141s）**，与 §11.2 的"改结构代价最低"共同支撑图范式在**复杂且演化**的指标
  体系上的总拥有成本优势。
