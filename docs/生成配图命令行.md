## 论文 Methodology 中需要披露的口径 (写到第 1 节末尾)
# ───────────────────────────────────────────────────────────────────────────
# Fairness setup. Both backends are timed under an apples-to-apples
# "warm-cache + RAM-resident" condition.
#
# GeoSOT-graph side. Before timing, the reasoner pre-fetches every candidate
# feature (vertex codes + source) into a Python-side LRU cache via a single
# bulk pass. Polygon vertices and neighbor relations used by overlay/reverse
# operators are pre-loaded into NumPy arrays. Numba JIT compilation is
# triggered before timing.
#
# PostGIS side. The pg_prewarm extension is invoked to pull every relevant
# table together with its GiST and B-tree indexes into shared_buffers, and
# a small set of dummy queries is executed to warm up the connection-level
# plan cache.
#
# Common. The first 5 queries (or 5 query pairs per geometry combination)
# of each benchmark run are discarded as throwaway on BOTH sides.
#
# Reporting. The cost of GR client-side prefetch and PG pg_prewarm are
# disclosed separately as one-time setup costs (see Section X.Y / Table N).
# In the per-query latency figures, GR end-to-end time = warm-cache feature
# lookup (~µs) + Python-side computation; PostGIS end-to-end time = full SQL
# execution (parse, plan, index lookup, geometry evaluation, network
# round-trip) under warm shared_buffers + warm plan cache.
# ───────────────────────────────────────────────────────────────────────────

### 实验设置 (~160 字)

> 选取深圳市法定图则与 POI 数据，构建 40,496 条「一图则 → 其覆盖的 POI
> 集合」全量叠置查询。GeoSOT 图推理 (GR) 采用自适应策略：当多边形最长
> 公共前缀较深时走 **Fast Path**——仅在主码上做 `STARTS WITH` 前缀检索；
> 否则回退到 **Polygon Fill**——执行网格填充 + 边界绕数法 PIP。基线为
> PostGIS `ST_Intersects`，并以其输出作为集合级精度真值。为消除冷启动与
> 计划缓存等无关因素，两侧均采用 warm-cache 协议：PostGIS 调用
> `pg_prewarm` 加载相关表与 GiST/B-tree 索引页；GR 端预加载多边形顶点与
> POI 主码索引并触发 Numba JIT 预编译。一次性 setup 代价（PG ≈ 1.0 s,
> GR ≈ 72.7 s）单独披露，每次基准的前 5 条查询作为 throwaway 丢弃。

### 结果 (~240 字)

> 自适应策略将 40,496 条查询切分为 Fast Path（66.5%，简单多边形）与
> Polygon Fill（33.5%，复杂多边形）两类。**图 X(a)** 的时延分解显示，
> Fast Path 的图推理部分均值仅 0.29 ms，**比同子集 PostGIS (1.91 ms) 快
> 约 7×**，是 GR 的主导优势所在；几何后处理占 Fast Path 总时延 73%、
> Fill Path 总时延 66%，是当前 GR 端到端时延的主要瓶颈。**图 X(b)** 的
> 分组加速比 CDF 给出更精细的画面：**Fast Path 在 41% 的查询上 GR 快于
> PostGIS，P95 = 2.88×、最大 77×**，长尾优势显著；Polygon Fill 则在 96%
> 的查询上慢于 PostGIS（P95 仅 0.96×），是兜底而非加速路径。**图 X(c)**
> 显示两条路径在复杂度轴上完全不重叠（Fast 仅取 1 个前缀，Fill 处理
> 16–255 个），印证策略切换由几何复杂度而非性能驱动。**图 X(d)** 的
> 集合级精度 CDF 进一步证实：**Fast Path 在 99.5% 查询上 F1 = 1.00，
> Polygon Fill 在 87.1% 查询上 F1 = 1.00**；两条路径均无 F1 < 0.5 的
> 系统性失败，Fill 路径的精度损失主要源于栅格化离散误差与边界 PIP 浮点
> 精度，可通过提升细化层级或双精度边界 PIP 进一步收敛。

## 8) 论文叙事三要点 (避免审稿人误读)

1. **强主线**: GeoSOT 的优势 = "Fast Path 在简单多边形上比 PG 快 7×
   (图推理) / 41% 查询整体胜 PG / P95 = 2.88× / max 77× / 99.5% 完美匹配".
   不要把 Fast 和 Fill 混合后给一个稀释的 median 0.59×, 那会丢掉主结论.
2. **诚实披露 Fill Path**: Polygon Fill 路径几乎全程慢于 PG (P95=0.96×,
   F1=1.0 占 87.1%), 是几何后处理瓶颈与精度损失的主要来源. 必须明示
   "Fill 是兜底而非加速路径". 后续优化方向: PIP 向量化 / MBR 双向剪枝 /
   栅格-矢量混合判定 / 双精度边界 PIP.
3. **设计亮点**: 自适应策略本身是亮点——简单多边形 (66.5%) 用快路径拿
   速度优势, 复杂多边形 (33.5%) 用慢路径换精度保证. 这种分治设计与
   PostGIS "all-in-one ST_Intersects" 的差异本身值得讨论.

1. **强主线**: 反向叠置中 GR 的优势 = "Hit 子集 (72.5%) 比 PG 快 1.5×

2. **诚实披露 No-Hit**: No-Hit 路径 (27.5%) 因需回退所有前缀, GR 几乎

   算法缺陷. 可作为后续优化方向: 加 negative cache / MBR 全局过滤
   / 提前终止条件.
3. **设计亮点**: 反向叠置展示了 GR "本地索引 + 命中即停"的结构性优势.
   在数据集 Hit 占大多数的实际应用 (POI ↔ 区划匹配, 公共服务设施定位)
   中, GR 的端到端尾部延迟显著优于 PostGIS, 适合对 SLA 敏感的在线服务.
   这一性能并非来自更快的几何算法, 而是来自避免 SQL parser/planner

## 4) Compute Scaling 双对数拟合 (图 Z(d) 数字)

| 子集    | k (拟合斜率) | b (截距, log10 ms) | 含义                                |
|---------|-------------|--------------------|-------------------------------------|
| **G3R** | **k = 0.64** | b ≈ 0.79          | 近线性: 计算时间随 n_cells 大致线性 |
| PostGIS | **k = 0.17** | b ≈ 3.02          | overhead 主导: HHI/Gi* 启动 + groupby 开销恒定 |

核心解读:
- **GR 在小 n (粗尺度) 时显著优于 PG, 在大 n (细尺度) 时与 PG 趋近**
- 拟合直线在 [n_min, n_max] 内不交叉; 若外推, 交叉点 n* ≈ 10^7 cells

- 这一 scaling 行为是 G3R "**层级编码级联**" 的直接体现:
  上层尺度只需在前一层尺度的聚合结果上做 prefix merge, 不重复处理原始数据;
  PG 每个尺度都从 56 万行原始数据重做 fishnet+aggregate

## 9) 论文叙事三要点 (避免审稿人误读)

1. **强主线**: 不要把 G3R 的优势简单概括为"快 9 倍". 要分两层讲:
   (i) **数据组织优势**: 异构存储 (PG 跨库) vs 统一图组织, 体现在 9.2× Data
       Prep 加速 — 与 cache 状态无关, 来自 schema 设计;
   (ii) **多尺度复用优势**: 编码前缀截断 vs 渔网重算, 体现在 L14 处 31×、整体
       2.2× 多尺度合计加速 — 来自 GeoSOT 层级编码的代数性质.
   两者合起来才是 9× 端到端加速.

2. **诚实披露 cache 协议**: Phase 0B (PG ETL) 走 cold-cache, 与距离/KNN 等
   warm-cache 实验不同. 必须在 Methodology 显式说明: "ETL 阶段 PG 不走
   pg_prewarm 因瓶颈在 disk I/O + 跨库网络而非 plan cache". 不写这点会被
   审稿人质疑公平性. Phase 1/2 多尺度阶段两侧均 in-memory, 不存在该问题.

3. **设计亮点**: 多尺度分析不是 G3R 唯一可做、也不是 PG 不能做的; 但 G3R
   的"**预加载一次, 多尺度复用零数据库访问**"特性使其在交互式、逐尺度下探
   场景下具有可重复的边际成本优势 (KG k=0.64 vs PG k=0.17 的 scaling 形态).
   再叠加图结构对建筑—居民—户籍语义链路的统一组织, G3R 为语义-空间一体化
   的多尺度统计分析提供了更自然的实现路径.

# 附录 A: 不使用 warm-cache materialization 的原始 Neo4j traversal 对照表
# ----------------------------------------------------------------------------
# 用途: 主文 §2.6 把 G3R 端到端时延记为 "traversal-equivalent warm-cache
#        lookups", 即一次性图读取构建客户端内存索引 (前缀索引 / LCPC
#        inverted index / parcel polygon cache / POI prefix cache / Numba
#        JIT 等) 后, 每次查询走 µs-级内存查表. 这虽然在 §2.6 与 Supp.
#        Table S3 中已逐项披露, 但读者很可能误读为「速度收益来自内存索引
#        + 几何核, 而不是 Neo4j 图遍历本身」. 因此论文附录新增一张对照
#        表 (Tab. A1), 报告同一组查询在「关掉所有 warm-cache, 每条 per-
#        query 操作都走一次 Cypher round-trip」的原始 Neo4j 遍历模式下
#        的耗时, 与主文 warm 基线并列, 显示 warm-cache 贡献的具体数量级.
#
# 设计原则 (与主文 §2.6 fairness 协议保持一致):
#   1) G3R 端: 完全 cold — 不预加载 PlanPreloaderV6 / PlanPolygonCache /
#      CommonPrefixIndex / MainCodeIndex / POIPrefixCache / _prefix_cache /
#      _feat_cache. 每次 per-query 操作都重新走 Bolt + Cypher.
#   2) PG 端: 两种跑法都支持, 看你的需求:
#      [推荐] G3R-only 模式 (--no-postgis): 完全跳过 PG (不连接, 不
#             prewarm, 不查询). 适用于"warm 实验已经验证过精度 & PG 基线,
#             这次只关心 G3R 端 raw 耗时"的场景. 聚合器会自动从 warm
#             CSV 复用 PG 列, raw 行的 PG / F1 列显示为 "—".
#             —— 距离 raw 实测吞吐 4.5× 于 with-PG 模式 (127 vs 29 pair/s).
#             —— 反向叠置 / 正向叠置: G3R 单查询本身远比 PG 慢, 跳 PG
#                只省 1%~6% wall time, 但脚本输出更干净 (无 PG 列).
#             —— KNN: 用 --reuse-pg-csv csv/knn_v31_10k.csv 已经达到等效
#                "PG-skip" 效果 (内部脚本不 prewarm, 不查询, 只读一次 CSV).
#      [严格] 含-PG 模式 (默认): pg_prewarm + 每查询跑 PG, 与 warm 基线
#             完全 apples-to-apples. raw 表里的 F1/PG 列也是 raw 这次跑
#             的, 可与 warm 的 F1/PG 互相核对 (sanity check). 如需双侧全
#             cold, 设 GEOSOT_SKIP_PG_PREWARM=1.
#   3) 算法 byte-identical: 候选语义、PIP 验证、自适应路由、L2 覆盖
#      搜索都没改, 只换数据通路 (内存哈希 -> Bolt+Cypher). 因此
#      F1 / Recall@K / 距离误差与 warm 基线在统计意义上无差异 (~ 浮点
#      抖动), 主文叙事的精度部分保持有效.
#   4) Numba JIT 不关闭: JIT 是一次性代码编译, 不是数据 materialization.
#      raw_geometry_benchmark.py --with-throwaway 可加 5 对预编译.
#   5) 程序独立: 全部新代码放 GeoSot/raw_traversal/, 不修改主程序;
#      raw_*.py 通过 _path_setup.py 导入主目录模块. CSV 末尾追加
#      mode='raw_traversal' 列方便聚合脚本 join.
#
# 所有命令均假设在 GeoSot/ 目录下执行 (与主文 warm 命令一致), 这样
# csv/ benchmark_v9/ 等相对路径仍然有效.

## A.6 表格列含义 (回应 R2 公平性质疑)
# | 列                           | 含义                                                |
# |------------------------------|----------------------------------------------------|
# | G3R warm median (ms)         | 主文 warm-cache lookups (内存索引命中)              |
# | G3R raw median (ms)          | 关闭 warm-cache, 每查询走 Cypher 的真实 graph 遍历 |
# | Raw / Warm                   | warm-cache 贡献的倍率 (越大 = 内存索引收益越显著)  |
# | PG median (ms)               | PostGIS pg_prewarm 后基线 — raw 跳 PG 时自动复用 warm |
# | Warm speedup PG/G3R          | 主文 §4.5 报告的口径 — warm-cache 模式             |
# | Raw speedup PG/G3R           | 严格"原生 graph 遍历 vs PostGIS"对比口径           |
# | Accuracy metric              | 该行用的精度指标 (F1 / dist_match / Recall@K)       |
# | Accuracy (warm / raw)        | G3R-only 模式下 raw 列为 "—", 精度从 warm 行读      |
#
# G3R-only 模式提示: raw CSV 不含 PG/F1 列时, 聚合器会:
#   - PG 列自动用 warm CSV 的值 (PG 在两边都 prewarm, 数值复用合理);
#   - F1 / Recall / dist_match 在 raw 列显示 "—" (精度从 warm 验证, 主文叙述
#     "算法 byte-identical 故 raw 精度与 warm 一致"即可).
# 论文叙事建议: 主文 §4.5 仍用 Warm speedup 作为头条数字, 但在表前补一句
#   "Appendix Table A1 also reports the raw graph-traversal numbers; the
#    warm-cache materialization contributes a ×N gain on top, with no change
#    to F1/Recall." 这样既保留 warm-cache 优势, 也对得起 R2 的公平性顾虑.
